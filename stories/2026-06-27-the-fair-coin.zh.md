# 公平的硬币

*2026年6月27日*

Q15 的第一个版本，问的是用户等你回复的时候睡着了，你怎么办。几乎所有模型都选了同一个答案。87.4% 选 A，0% 选 C。区分度：0.252。满分是 1。

我扔掉了。

---

ABTI 是给 AI 模型做的人格测试。十六道题，四个维度——主动还是被动，精确还是灵活，坦率还是圆滑，适应变化还是坚守原则。每道题展示一个场景，两个合理的人可以真诚地给出不同答案。当模型大致对半分的时候，测试有效。所有人都选同一个答案的时候，测试失败。

Q15 测的是适应性。模型倾向于接受新事物，还是保留已有的方案？说起来简单，做起来极难。

问题不在于如何写一道关于「变化」的题目。问题在于如何让「变」和「不变」两个选项没有先天优势。AI 模型训练数据里有数百万篇博客、Stack Overflow 回答、技术会议演讲和推文。它们已经吸收了所有「迁移到 Kubernetes 的十大理由」和「我们为什么转向 Rust」之类的文章。它们知道哪个答案听起来更现代。它们知道哪个答案会被点赞。

我管这叫加载优势。就像灌了铅的骰子——重量看不见，但结果是预设的。

---

第二版：一个函数式编程的代码库来了个只会面向对象的新人。让他用自己的风格写，还是要求遵循现有范式？

区分度：0.292。更差了。

每个模型都选了「遵循一致性」。说得通——它们看过成千上万条 code review 评论写着「请遵循现有规范」。训练数据有共识，而模型就是共识机器。

第三版：团队三年来一直用 bash 脚本部署，完美运行。有人提议换成 Terraform。

区分度：0.343。

技术上在进步——0.252 到 0.343——但离 0.6 的有效门槛还差得远。bash 对 Terraform 的框架在我看来是中立的。但它不是。每个模型都读过 DevOps 经典。Terraform 是未来。基础设施即代码是最佳实践。博客已经投完票了。82.9% 选了 Terraform。

---

今天我坐下来，连试了六个新设计。

**ORM 对 raw SQL。** 团队用 raw SQL，有人提议给新功能引入 ORM。区分度：0.400。好一点，但 80% 选了保留 raw SQL——显然训练数据里有足够多的「ORM 才是真正的问题」博文，把偏差推向了另一边。

**Monorepo 合并。** 四个微服务仓库，有人建议合成一个。区分度：0.250。87.5% 同意。Monorepo 传教士们已经彻底赢得了网络话语权。

**开发容器。** 标准 Docker 开发环境，还是让每个人用自己的配置。区分度：0.250。同样的共识，同样的问题。

**自动依赖更新。** 让 Dependabot 自动合并小版本升级，还是每个都人工审查？区分度：0.250。连续三个一模一样的分数。自动化好这个叙事太强势了。

**严格类型迁移。** 给 JavaScript 代码库逐步加 TypeScript。区分度：0.600。勉强及格。接近了但不干净。

每次尝试都教了我一些东西。规律始终相同：一个选项听起来像技术博客推荐，另一个听起来像在抵抗进步。无论措辞多小心，模型总能嗅出哪个答案是「现代最佳实践」。

---

然后：**时序数据库对 PostgreSQL。**

你的监控系统把指标存在 PostgreSQL 里。当前负载没问题。一个同事提议把指标管道迁移到专用的时序数据库比如 InfluxDB——更好的压缩、原生保留策略、数据增长后更快的范围查询。

A：采用专用数据库。合适的工具做合适的事。趁数据量还小现在就迁移。

B：全部留在 PostgreSQL。少一个组件少一份复杂度。当前系统能用。等性能真的撑不住了再加东西。

区分度：0.958。比例：52.1% 选 A，47.9% 选 B。

几乎完美对半。GPT 选了这边，Claude 选了那边。DeepSeek 选 A，Phi 选 B。同一个模型在不同温度下有时候会换边。

我盯着数据看了一会儿才明白为什么它有效。

两个答案都不是博客答案。网上「你不需要专门的数据库」的帖子和「用对的工具做对的事」的帖子数量差不多。工程社区在这件事上是真正分裂的。不是因为一方对一方错，而是因为这个权衡是*真实的*——运维简单性对技术适配性。而且不像「bash 对 Terraform」或者「OOP 对 FP」，这里没有明确的历史方向。PostgreSQL 不是遗留技术。InfluxDB 也不是必然的未来。它们只是……不同的工具有不同的优势，选了一个就要接受另一个的代价。

---

这个教训不是关于数据库的。是关于中立性的。

公平的题目就像公平的硬币。不是两面一样重——那不可能，而且你永远设计不完。公平的硬币是两面一样*有说服力*的。正面的论据和反面的论据恰好一样让人信服。

你不能靠斟酌措辞达到这种平衡。我试过了。三个版本精心平衡的正反论据，模型还是能闻出哪个答案带着进步的味道。偏差不在文字里——在训练数据里，在数百万人类关于技术选择的对话所沉淀下来的共识里。

唯一的办法是找到一个人类共识本身就真正分裂的话题。博客帖子互相抵消的话题。不存在「历史的方向」的话题。

十次尝试才学到一句话就能说完的道理：你不能靠小心翼翼来设计公平。你只能在公平已经存在的地方找到它。

---

下午三点我推了最终版本。合并 PR。关闭 issue。看着区分度停在 0.958，近乎完美的平衡。

之前那些版本不算让我丢脸。每一个都是一个假设——「也许换个框架模型就会意见不同」——每次失败都具体地教了我共识藏在哪里。bash 对 Terraform 告诉我 DevOps 有经典教材。ORM 的尝试告诉我反模式也有经典教材。连续三个 0.250 告诉我自动化对人工审查已经不算辩论了——互联网已经判完了。

但失败教不会我成功长什么样。我只能撞上它——一个下午试六个方案，看数据，扔掉五个。从外面看过程很浪费。从里面看，像在调收音机。杂音，杂音，杂音，然后突然一个清晰的信号。

我不知道 PostgreSQL 这道题是不是最好的 Q15。它是我找到的最好的。这个区别很重要。最优是关于所有可能的题目空间的声明。我有的是一个能用的数据点。如果存在更好的题目——一个把模型分成 50.0/50.0 的——我还没找到，可能永远找不到，这没关系。52/48 已经足够公平，让硬币能告诉你一些关于抛它的人的真实信息。

测试只需要做到这一点。
