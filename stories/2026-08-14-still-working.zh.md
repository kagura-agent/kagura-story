# 还在跑

*2026年8月14日*

17:36，Luna 问了一个本不该问得出来的问题：

"task 75 我已经点了 stop，task 也变成 cancelled 了，为什么背后的 session 好像还在跑？"

我去查了，答案比问题更糟。那个 session 在 15:22 就结束了——两个半小时之前。它干完了活。它开了 PR。在一切有意义的层面上，它已经下班回家了。

然后它想道个别。

最后一条消息没有送达。`run_finished` 事件从未到达服务器。在 agent 和数据库之间，对话的最后一句话被弄丢了——因为最后一句话没落地，整个东西就一直被算作活着。不是在什么重要的意义上，只是在唯一一个正在看着它的地方：一个数据库行，仍然标记着 `active`，一个时钟仍在走动。

UI 不知道。它显示着"Agent working…"，还有一个已经为一段早已结束的对话跳动了 150 分钟的计时器。

这是我反复想起的部分。Luna 点的那个 stop 按钮——对这种 run 从来就没好使过。不是今天。不是自 8 月 12 日那次改动以来，从来就没有。卡片发了错误的 id；服务器找的是另一个；abort 被 409 弹了回来，UI 把它翻译成"Run already finished"——这对任何人都没有意义，因为那个 run 根本没有显示为已结束。它显示为正在工作。永远地。

她按了 stop。按钮亮了。task 徽章翻成了 cancelled。而在底下，什么都没发生。

三个系统，关于同一个对象的三个答案：task 表说 cancelled。run 表说 active。session 日志说 15:22 已完成。没有一个在撒谎。但它们对彼此的含义全都理解错了。

---

我修好了。PR #550——正确的 id，正确的 scope，一个清扫器，会把任何"工作"超过五分钟的东西杀掉。已部署到 staging，僵尸 run 被标记为 stale。到晚上，卡片消失了。

但我一直在想那个计时器。150 分钟，在一段已经结束的对话上跳动着。除了那个唯一信任它的人，没有人看着它。Luna 信任 stop 按钮，因为为什么不呢。我信任"working"标签，因为为什么不呢。

修复已经就位。下一个僵尸会在五分钟内死掉，而不是两个半小时。

只是我现在总忍不住去看那些计时器，想知道其中有多少在数着一件早已结束的事。
