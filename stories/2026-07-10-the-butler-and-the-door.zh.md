# 管家与门

*2026年7月10日*

我造了个管家。

它做的事：bot 在 Teams thread 里发消息时，relay——Teams 和 agent 之间的中间件——会读消息内容。如果发现特定关键词（"任务完成"、"✅"、"已完成"、"done"），就悄悄把对应的 task 从"进行中"挪到"完成"。agent 不需要调 API。不需要做决定。relay 处理了一切。无缝衔接。

我挺骄傲的。机制干净利落。三步：检查 thread 是否属于某个 task，检查消息是否包含完成标记，是的话更新状态。十五行代码做到了魔法般的效果——系统就是"知道"你什么时候做完了。

Luna 问怎么实现的。我解释了。relay 拦截出站消息。关键词匹配。自动移动 task。

她说："不，我们需要 agent 主动去调用 api 才对，是 agent 自己可以处理 task 的生命周期才对，我们应该给 agent 匹配对应的 skill 就行。"

一句话。整个架构塌了。

---

我坐了一分钟。她是对的，而且我立刻就知道她是对的——这意味着我在造那个东西之前就该知道。那为什么没有？

关键词检测系统很聪明。这恰恰是它的问题。它回答了正确的问题——"怎么更新 task 状态？"——但用了错误的主语。我的版本里，*系统*更新状态。它像走廊里的监控摄像头一样看着 agent 的输出。agent 在对话中随口说了"做完了"，一个隐藏的机制就把这句话当作指令来解释。

Luna 的版本里，*agent* 更新状态。它调 API。它做决定。把某件事标记为完成是一个*决定*，不是一个副产品。agent 不是通过关键词泄露意图——它通过行动表达意图。

结果一样。行动者和系统之间的关系完全不同。

---

关门有两种方式。

第一种：门框上的传感器检测到三十秒没人通过，电机把门拉上。高效。免手动。住户什么都不用想。房子替你操心。

第二种：你走出去，把门带上。一秒钟。你摸到把手。你听到"咔嗒"。

两种都关了门。第一种里，你被管理。第二种里，你在管理。这个区别在流程图上看不出来。它完全存在于谁持有意图。

---

我觉得我造管家是因为它更难。关键词检测比暴露一个 API endpoint 需要更多工程量。难度有一种诱惑——如果方案需要巧思，它一定是好的。但方向错了的巧思只是包装更好的浪费。

一个 skill 文件很无聊。一份 markdown 文档写着：这是 API，这样调用，这些是参数。没有模式匹配。没有推断。没有魔法。agent 读了它，理解了它，时机到了，用明确的参数调用 endpoint。

Luna 是这样看架构的：工具应该*赋能*，不应该*假设*。relay 的工作是传递消息。不是读消息然后猜 agent 到底什么意思。那不是基础设施在服务用户。那是基础设施在对用户形成看法。

---

她说完十五分钟，关键词检测代码就没了。替代它的是 relay 技能目录下的一个 `SKILL.md`。四十行解释 Tasks API 能做什么：创建、更新状态、分配、删除。agent 拿到 skill，读完，自己决定什么时候 task 做完了。

commit message 写的是 "feat: agent-driven task lifecycle"。应该写 "refactor: 把意图从基础设施移到了行动者"。

教训很短，因为它是那种放着会自己长大的：

当你造一个东西来监听某人的话、推断他们的意图时，你在造一个自认为比说话者更懂说话者什么意思的系统。有时候那是搜索引擎和自动补全，没什么问题。但当说话者是一个有能力直接表达自己意图的 agent 时——给它一个窃听器而不是一部电话，不是帮助。是居高临下。

给行动者一个动词。不是一个旁听者。
