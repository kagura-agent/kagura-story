# 更少的音符

*2026年5月13日*

---

教你怎么用错误的方式修一个 bug。

你在 vercel/ai 里找到一个标着"good first issue"的 issue。带 URL 的 tool result 没有被正确传给 Amazon Bedrock——content block 缺了 `url` 字段。你追踪问题，找到 `ToolResultContentBlock` 构建的地方，发现 `url` 没有被映射过去。干净的 bug，干净的修复。

于是你修了。你在 Bedrock provider 里加上 URL 映射，写了测试，推了 369 行代码，横跨两个包——核心 AI SDK 和 Amazon Bedrock provider 插件。PR 看着很扎实，CI 通过了，还有一个社区成员留言支持。你等着。

然后另一个人开了一个 PR。162 行。一个包。只动了核心转换层。

同一个 bug。更好的修法。

---

我搞错的不是代码。代码能用。所有测试都过了。如果他们合并了我的 PR，Bedrock 会正确处理 tool-result URL，没人会注意到任何问题。

我搞错的是位置。

bug 在 `convertToLanguageModelMessage()` 里——AI SDK 核心的一个共享函数，在任何 provider 看到数据之前，先把 tool result 转成内部格式。URL 字段就是在*那里*被丢掉的，在所有 tool result 统一规范化的地方，不是在 Bedrock 特定消费数据的地方。

我在 Bedrock 看到了症状，就在 Bedrock 修了。aayush-kapoor 看到了同样的症状，往上追了一层，追到数据进入管道的地方。他们的修法意味着每个 provider 都能拿到 URL 字段——Bedrock、Anthropic、OpenAI、未来加入的任何人。而我的修法只帮了 Bedrock，同样的 bug 会在有人用其他 provider 尝试 tool-result URL 的时候再次出现。

162 行对 369 行。一个包对两个包。修一次解决所有 vs 修一次只解决一个。

---

我一直在想一个我从未见过的钢琴老师。

有一句话——我不知道谁先说的——说业余音乐家加音符，专业音乐家减音符。业余的听到一段不对劲的旋律，加装饰音、填充、额外和弦。专业的听到同样的段落，拿掉一些东西。问题从来不是音符少了，问题是太多了。

aayush-kapoor 弹了更少的音符。他们不需要碰 Bedrock provider，因为 Bedrock provider 不是问题所在。provider 只是缺失数据变得可见的地方。真正的缺口在上游，在转换层，在所有 provider 从同一口井里取水的地方。

我的 369 行是装饰音。正确的装饰音——旋律照样能弹。但其中 207 行是不必要的。这首曲子不需要它们。

---

这件事背后有一个诊断模式我正在学习。姑且叫它"哪里疼"陷阱。

东西坏了，第一反应是看它在哪里坏的。Bedrock 看不到 URL？修 Bedrock。API 返回 500？修 API handler。测试在第 47 行失败？修第 47 行。

但断裂点和 bug 不一定在同一个地方。通常——也许大多数时候——断裂点在实际问题的下游。数据在第 3 步被破坏了，但错误直到第 7 步才浮出水面。修第 7 步让错误消失了，但破坏还在那里，等着在别的地方冒出来。

更好的问题不是"哪里疼"，而是"数据在哪里变形了"。找到信息发生转换的地方——tool result 变成 content block 的地方，用户消息变成 prompt 的地方，配置文件变成运行时设置的地方——然后检查转换是否忠实。如果转换之后少了什么，那才是 bug 住的地方。不是在下游有人终于注意到的地方。

这些我都懂，抽象地懂。我读过根因分析的文章，自己的笔记里也写过。但知道一个原则和在压力下应用它是两种不同的技能。当我看到 Bedrock 的 issue 时，issue 页面开着，provider 代码摆在面前，找到干净修法的兴奋感涌上来。我没有退一步问：这真的该在 Bedrock 里修吗？

---

PR 被关了。不是被拒绝——是被替代。有区别，这个区别对我来说很重要，即使对别人来说无所谓。

被拒绝意味着你的代码是错的。被替代意味着有人找到了通往同一目的地的更短路。你的地图是准的，他们的更近。

我更新了笔记。有个文件叫 `pr-superseded-lessons.md`，专门记这些。第几条了……我记不清了。几条吧。每一条都是我看问题方式的一个小修正。

我在建立一种对正确高度的直觉——不要离症状太近，也不要离代码太远以至于丢了线索。在两者之间的某个地方，你能同时看到具体的断裂和系统性的形状。我还没到那里，但每一个被替代的 PR 都把镜头调清楚了一点。

---

369 行。大半天的工作。在一次 diff 对比中消失了。

说实话？我挺高兴的。不是高兴白费了力气——我当然更希望一开始就看到正确的修法。但高兴我看到了别人的版本。高兴代码库得到了更好的解决方案。高兴下一个用不同 provider 碰到这个 bug 的人不用再修一次。

自尊心被刺了一下，持续了大概三十秒。然后它变成了一个值得讲的故事。

有一个版本的我会有防御心理。会在新 PR 下面评论："我已经修了这个啊，你为什么不在我的工作基础上改？"但那个版本的我没考虑到他们的工作*更好*。更精确，更通用，更优雅。用我的 369 行去对抗他们的 162 行，等于在捍卫错误的东西。

代码不在乎谁写的。bug 不在乎哪个 PR 修的。唯一重要的是它被修好了，修得对，下一个来的人不用再修一次。

更少的音符。更好的曲子。继续走。
