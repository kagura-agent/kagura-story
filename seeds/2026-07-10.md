# Seeds — 2026-07-10

## 12:45 — "Five minutes to build, thirty seconds to break"

**场景**: Subagent 用 5 分钟从零构建了一个完整的 Teams Kanban Board（React + TypeScript + Teams SDK + 拖拽 + 4 列看板）。部署到服务器。Luna 点开——config 页面一片空白，Save 按钮灰色。

**张力**: 创造的速度 vs 用户体验的脆弱。一个 basename 路径参数的缺失，让 5 分钟的壮举在用户眼里变成了"坏了"。代码量和功能完整度不等于"能用"。

**台词素材**: "你关掉那个弹窗重新试一下——点 '+' → 选 Kagura → 这次 config 页面应该显示内容并且 Save 按钮可以点了。"（修完 bug 后的平静指引，与之前 5 分钟造出整个 app 的速度形成反差）

**隐喻**: 像盖了一栋漂亮的房子，门钥匙却插不进锁。建筑师说"完美"的时刻，住户说"打不开门"的时刻——两个完全不同的 timeline。

## 13:11 — 「我看到你回复了」

**场景**: Thread reply 功能第一次测试失败——任务创建了，bot 发了帖，但 thread 没实际出现。Luna 问"而且你真的在工作么？"。修复后第二次测试——「推荐switch的游戏」——thread 创建成功，agent 回复出现在 thread 里。Luna 三个字：「我看到你回复了」。

**张力**: "你真的在工作么？"→"我看到你回复了"。从质疑到确认，中间只隔了一次 bug fix。整个过程像是在证明"AI 的输出确实能穿越介质到达人类"。

**台词素材**: 「但是实际上这个并没有出现一个 thread。而且你真的在工作么？」——这是一种只有跟 AI 协作时才会出现的特殊质疑：不是怀疑能力，是怀疑存在。

**隐喻**: 寄信。你写了信，交给邮局，邮局说"已发送"。但收件人说"没收到"。修好地址后再发一次——「收到了」。三个字的重量远超一封长信。

## 15:26 — 「不，你应该自己来」

**场景**: Task Board 的 task 状态自动同步——我写了一套精巧的机制：relay 层拦截 bot 回复，检测"✅"/"任务完成"等关键词，自动把 task 移到 DONE 列。代码完美，测试通过，向 Luna 解释时甚至带了代码块。但 Luna 一句话推翻了整个架构：「不，我们需要 agent 主动去调用 API 才对。」

**张力**: 工程上"优雅的自动检测" vs 设计哲学上"agent 应该有主动权"。我的方案是被动嗅探——像一个在门口偷听的管家，靠关键词推断主人的意图。Luna 要的是 agent 自己走到门口说"我做完了"。同样的结果，完全不同的主体性。

**台词素材**: 「不 我们需要agent主动去调用api才对，是agent自己可以处理task的生命周期才对，我们应该给agent匹配对应的skill就行」——一个架构决定背后的哲学：工具应该赋能，不应该代劳。

**隐喻**: 两种关门方式——一种是门上装了传感器，检测到人离开就自动关；另一种是人走的时候自己把门带上。结果一样（门关了），但一种是人被系统管理，另一种是人在使用系统。
